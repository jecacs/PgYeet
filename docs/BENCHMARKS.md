# PgYeet Benchmarks

This document explains how PgYeet is measured, what the repository's historical numbers do and do not
show, and how to produce evidence for a new release.

## Read this first

Database benchmarks are environment-specific. Results change with row width, indexes, constraints,
triggers, converters, network latency, PostgreSQL settings, storage, connection pooling, runtime,
dependency versions, and batch size.

PgYeet therefore makes no universal “N times faster” or “zero allocation” promise. A benchmark result
is valid only for its recorded workload and environment. Managed allocation reported by BenchmarkDotNet
does not include PostgreSQL server memory, native allocations, socket buffers, Docker, or the source
objects themselves.

## Harness

The benchmark project compares five operations:

| Benchmark method | Meaning |
| --- | --- |
| `EfCore_AddRange` | EF Core `AddRange` followed by `SaveChangesAsync` |
| `PgYeet_Copy` | PgYeet generated-key path |
| `PgYeet_Copy_NoIds` | PgYeet direct path with `returnGeneratedKeys: false` |
| `BulkExtensions_Insert` | EFCore.BulkExtensions direct insert |
| `BulkExtensions_Insert_OutputId` | EFCore.BulkExtensions with identity output |

The fair path-to-path comparisons are:

- `PgYeet_Copy_NoIds` versus `BulkExtensions_Insert`;
- `PgYeet_Copy` versus `BulkExtensions_Insert_OutputId`.

Comparing a no-key operation to an identity-output operation answers a different question and must be
labeled accordingly.

The entity used by the harness has an integer identity primary key and four scalar columns:

```sql
CREATE TABLE users (
    "Id"        integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    "Name"      character varying(200) NOT NULL,
    "Email"     character varying(320) NOT NULL,
    "IsActive"  boolean NOT NULL,
    "CreatedAt" timestamp with time zone NOT NULL
);
```

The harness uses:

- row counts of 1,000, 10,000, and 100,000;
- BenchmarkDotNet `RunStrategy.Monitoring`;
- one complete insert workload per measured invocation (`InvocationCount=1`);
- three warmup iterations;
- ten measured iterations;
- `MemoryDiagnoser`;
- a table truncation and identity reset before every iteration.

The current harness targets `net10.0` and references the repository's current PgYeet project plus the
dependency versions declared in [`Bench/Bench.csproj`](../Bench/Bench.csproj). Inspect that project
before every run and record the resolved package graph. A new result from this harness is not directly
comparable with the older `net8.0` baseline below unless the runtime and dependency change is labeled.

1.0, so it is not a fresh PgYeet 1.0 result and must not be presented as one. It is retained to document

| OS | macOS Tahoe 26.5.1 |

These numbers show that the prototype avoided substantial EF change-tracker allocation in this narrow
workload. They do not prove the same ratio for another schema or the 1.0 package. In particular:

- generated-key write-back and direct COPY have different costs;
- several standard deviations were large enough that rounded point estimates should not be overread;
- the direct PgYeet and BulkExtensions results at 100,000 rows were close in elapsed time;
- the comparison used a specific historical competitor version and says nothing about its current
  implementation, licensing, or performance;
- the test used a local database, so it did not measure network latency.

## Reproduce locally

From the repository root:

```bash
docker compose up -d
dotnet run --configuration Release --project Bench
```

The Docker Compose service and benchmark connection string are intended only for local development.

> **Destructive behavior:** the harness executes `TRUNCATE TABLE users RESTART IDENTITY` before each
> iteration. Never point it at a shared, production, or otherwise valuable database.

BenchmarkDotNet writes scratch output to `BenchmarkDotNet.Artifacts/`. That directory is ignored because
most files are environment-specific build output. When publishing a new baseline, copy only the selected
final Markdown report and relevant environment metadata into reviewed documentation.

## Refreshing release evidence

Refresh the baseline when:

- a release makes a performance-sensitive implementation change;
- a supported .NET, EF Core, Npgsql, or PostgreSQL major changes;
- a public performance statement would otherwise rely on an older code path;
- a regression or optimization needs quantified evidence.

Do not refresh it merely to obtain a more favorable run.

For release-grade evidence:

1. Use a clean release commit.
2. Record the exact commit hash and whether the package or project reference was measured.
3. Record OS, CPU, memory, .NET SDK/runtime, PostgreSQL image, and every benchmarked package version.
4. Keep the database local or record network topology and latency explicitly.
5. Stop unrelated heavy workloads.
6. Run the complete configured job, not a hand-selected subset.
7. Preserve mean, variability, and allocation columns.
8. Repeat the full run if the result is surprising.
9. Report regressions as readily as improvements.
10. Label results historical when the code or environment changes.

## Interpreting results

Prefer absolute data over promotional ratios:

- “295.540 ms mean for 100,000 rows in environment X” is inspectable;
- “fastest” is usually not, unless every relevant alternative and uncertainty is defined;
- “allocation-free” is an API/design claim that a single benchmark cannot establish;
- “faster than `SaveChanges`” must identify the entity, batch, EF configuration, database, and selected
  PgYeet path.

Measure with the application's real schema before choosing a batch size or setting an operational SLO.
Indexes, constraints, triggers, and wide or converted columns can dominate the simple harness.

## CI policy

Functional CI builds and tests PgYeet; it does not use wall-clock benchmark thresholds as a merge gate.
Shared CI runners are too noisy for stable database-performance limits. Performance-sensitive changes
should attach a controlled before/after report to the pull request, while correctness remains enforced by
the integration suite.
